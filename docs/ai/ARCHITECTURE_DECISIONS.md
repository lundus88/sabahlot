# SabahLot — Architecture Decision Records (ADR)

Each decision is recorded once and never silently overridden. If a later sprint needs to change one, add a new ADR that supersedes it explicitly (do not edit history).

---

### ADR-001
**Decision:** Every cloud-writable local object (land record, geometry, point, party) reuses its existing client-generated `id` as the stable cloud primary key. IDs are never regenerated on retry.
**Reason:** Enables idempotent create (see ADR-002) and satisfies the invariant `one local object = one cloud row`.
**Consequences:** Non-UUID legacy local IDs (from before `crypto.randomUUID()` was consistently available) cannot be uploaded automatically — they return `legacy_id_requires_migration_mapping` / `legacy_child_id_requires_mapping` and must go through a future, explicit migration-mapping sprint.
**Status:** Accepted (Sprint 02C-1, extended Sprint 02D-1A).

### ADR-002
**Decision:** Create uses plain `INSERT`, never `UPSERT`. A retry that hits Postgres `23505` (unique violation) is resolved by reading the existing row (under RLS) and comparing its allowlisted content against the requested payload.
**Reason:** `UPSERT` would silently overwrite a row with different content on retry, masking the difference between "this exact request already succeeded" and "someone/something else changed this row." A HIGH-severity finding in Sprint 02C-1's independent review confirmed the naive version of this check (ownership-only, no content comparison) was unsafe.
**Consequences:** Same-id + same-content retry → verified idempotent success. Same-id + different-content retry → `duplicate_conflict`, row and cache untouched, no automatic retry. Unreadable/inaccessible duplicate → `not_found` / `not_found_or_forbidden` (never reveals whether the id belongs to another user).
**Status:** Accepted (Sprint 02C-1 Patch 1). Do not use `UPSERT` in any future child-table sprint without a new ADR explicitly justifying it.

### ADR-003
**Decision:** Update uses optimistic concurrency: the UPDATE statement itself filters on both `id` AND `updated_at = expectedUpdatedAt` atomically (never a separate SELECT-then-UPDATE).
**Reason:** Prevents a stale client from silently overwriting a row that changed elsewhere (another device, or a concurrent save) — the atomic filter means a stale caller's UPDATE matches zero rows instead of racing.
**Consequences:** A zero-row UPDATE result is ambiguous (not-found vs. not-owned vs. stale) and requires a read-only diagnosis step afterward, which must never reveal existence of another user's row (see ADR-004) and must never update the cache.
**Status:** Accepted (Sprint 02C-1, reused identically for geometry in Sprint 02D-1A).

### ADR-004
**Decision:** When RLS makes "row doesn't exist" and "row belongs to another user" indistinguishable, both cases are reported identically (`not_found` / `not_found_or_forbidden`), never as a distinct `forbidden`.
**Reason:** Returning a distinct "forbidden" for another user's row would leak the row's existence to a caller who has no right to know it — an enumeration side-channel.
**Consequences:** Slightly less precise error messages for legitimate not-found cases, in exchange for closing the enumeration channel entirely.
**Status:** Accepted (Sprint 02C-1, Sprint 02D-1A).

### ADR-005
**Decision:** Owner/user identity (`owner_id`, `captured_by`) is always derived server-side from `supabase.auth.getUser()` inside the repository/coordinator layer. It is never accepted as a field on any create/update input type, and the database payload is built as `{ ...allowlistedFields, id, owner_id: sessionUserId }` — session-derived fields spread LAST so they always win even if the allowlist ever regresses.
**Reason:** Structural prevention of owner/attribution spoofing, independent of RLS. A MEDIUM finding in the Sprint 02D-0 audit noted that `land_points`' RLS does not itself constrain `captured_by` on the linked branch — this ADR is the compensating application-layer control for that gap.
**Consequences:** Any future child-table (points, parties) write path MUST follow this exact pattern; a code reviewer should reject any create/update input type that includes an owner/user field.
**Status:** Accepted (Sprint 02C-1, extended Sprint 02D-1A; mandatory for points per Sprint 02D-0A).

### ADR-006
**Decision:** Authorization boundary is RLS, not application code. No repository function accepts or checks an owner id passed by the caller; every table's INSERT/UPDATE/SELECT/DELETE policy independently enforces `owner_id = auth.uid()` (directly, or via `EXISTS` through the parent `land_records` row for child tables).
**Reason:** Defense that survives an application bug — even if a coordinator function had a logic error, RLS is the actual enforcement layer.
**Consequences:** Every new child table's migration must include RLS policies proven (via written cross-user test scenarios) before any write code is built against it.
**Status:** Accepted (Sprint 01B-1 onward).

### ADR-007
**Decision:** Client-side cache (`sabahlot_cloud_land_records_v1:<user-uuid>`) is namespaced by the authenticated user's UUID. There is no "current user" global; every cache function takes the user id explicitly.
**Reason:** Prevents a stale/wrong cache from becoming active after logout or account switch, and makes cross-user cache leakage structurally hard to introduce by accident.
**Consequences:** Anonymous sessions never read or write this cache at all (no cloud query happens for them in the first place).
**Status:** Accepted (Sprint 02B).

### ADR-008
**Decision:** Parent-then-child staged sync, not a database transaction/RPC. `land_records` is created/updated first (already merged); geometry, points, and parties are each written as independent, individually-atomic operations after the parent exists. No RPC or Postgres transaction function wraps multiple tables.
**Reason:** PostgREST (via `@supabase/supabase-js`) has no native multi-table transaction; building one requires a new Postgres function, which is a migration — out of scope for a frontend/repository sprint. A staged approach with honest partial-failure reporting is safer than a false sense of atomicity.
**Consequences:** A child write can fail independently of the parent or of other children. The UI/consumer must handle and clearly display `partial_sync` (see ADR-009) rather than assuming all-or-nothing.
**Status:** Accepted (Sprint 02D-0A).

### ADR-009
**Decision:** Sync status uses specific, honest labels — `record_synced`, `geometry_synced`, `points_synced`, `parties_synced`, `core_record_synced`, `partial_sync`, `points_out_of_sync` — never a generic `synced` for a write flow, and never `full_record_synced`.
**Reason:** A bare "synced" (or a premature "full") would imply more of the record is safely in the cloud than actually is. `core_record_synced` explicitly excludes `documents`, which is out of scope until its own sprint.
**Consequences:** UI copy (when eventually built) must reflect the specific state, not collapse it to a generic "saved" indicator.
**Status:** Accepted (Sprint 02C-1 for the parent-only states; Sprint 02D-0A for the child/core states).

### ADR-010
**Decision:** `full_record_synced` must not be used until `documents` is implemented and confirmed synced alongside parent + geometry + points + parties.
**Reason:** Documents are explicitly out of scope for the current cloud-write sprint series (see ADR-012). Using "full" before they exist would be a false claim.
**Consequences:** `ChildSyncState` / `WriteSyncState` type unions intentionally omit `full_record_synced` as a value at all — it is not merely "unused," it does not exist as a reachable state today.
**Status:** Accepted (Sprint 02D-0A).

### ADR-011
**Decision:** Points cloud write is **create-only** in Sprint 02D. No UPDATE, no DELETE, no `updated_at`-based conflict control for points.
**Reason:** `land_points` has no `updated_at` column and no update trigger (confirmed by direct migration audit, Sprint 02D-0/02D-0A) — building optimistic-concurrency UPDATE for points would require a new migration, which is out of scope. Building UPDATE without conflict control would risk silent stale overwrites.
**Consequences:** Editing a point locally after it has been cloud-synced must surface a `points_out_of_sync` state (not a false `points_synced`), never silently re-upload as a new row, never delete+recreate as a workaround.
**Status:** Accepted (Sprint 02D-0A). Revisit only via a new ADR after an explicit owner decision to add `updated_at` to `land_points` (which requires a migration sprint).

### ADR-012
**Decision:** Documents and Supabase Storage (bucket creation, file upload, signed URLs, document metadata write) are entirely out of scope for the current cloud-write sprint series and will be their own, later, separately-scoped sprint.
**Reason:** Established since Sprint 02A's architecture review; reconfirmed at every subsequent gate (02D-0, 02D-0A).
**Status:** Accepted, standing.

### ADR-013
**Decision:** Delete (and archive) for geometry, points, and parties is deferred — not built in Sprint 02D.
**Reason:** Owner decision (Sprint 02D-0A) to keep the initial cloud-write surface minimal and reversible; delete semantics (hard vs. soft, cascade behavior, audit trail) need their own explicit design decision.
**Status:** Accepted, standing until a future sprint explicitly scopes delete.

### ADR-014
**Decision:** `land_parties.id_number` (government ID number) is never sent to the cloud in Sprint 02D. Only PDPA-minimal fields (name, role, contact reference, general notes) are cloud-writable.
**Reason:** `id_number` is flagged HIGH SENSITIVITY in its own migration comment since Sprint 01B-1; no column-level encryption/masking exists yet, and PDPA Malaysia treats government ID numbers as sensitive personal data requiring extra protection.
**Consequences:** `id_number` remains local-only until an explicit owner decision on encryption/masking strategy, tracked as a standing owner-decision item.
**Status:** Accepted (Sprint 02D-0A).

### ADR-015
**Decision:** One active geometry per `land_record` is enforced at the application layer (a pre-INSERT check against existing geometries for the same parent), not by a database unique constraint.
**Reason:** No unique constraint exists on `land_record_geometries` and adding one requires a migration, out of scope for Sprint 02D-1A.
**Consequences:** This has a documented, accepted TOCTOU race under true concurrent requests (two simultaneous creates for the same parent could theoretically both pass the check) — tracked as a MEDIUM finding, not silently hidden, and not a blocker for the sprint that introduced it.
**Status:** Accepted with known limitation (Sprint 02D-1A). Revisit if concurrent-create abuse is ever observed in practice.

### ADR-016
**Decision:** No third-party device or vendor brand name (e.g. specific GNSS receiver/smartphone model names) may appear in any user-facing string, code identifier, filename, or public documentation for the Handheld GPS module. Internal accuracy targets (e.g. "0.5 m field reference") are chosen to be reasonable for a class of rugged Android GNSS devices generally, and are recorded and discussed only in private planning context (chat with AI collaborators, non-public sprint notes), never copied into the codebase or docs directories.
**Reason:** SabahLot must not be seen as designed around, endorsed by, or imitating any specific commercial hardware vendor. The product's existing "preliminary reference only, not affiliated with JTU Sabah" disclaimer stance extends to hardware neutrality.
**Consequences:** Accuracy thresholds and quality grades (`gps-quality.ts`) must be justified in generic terms ("typical rugged GNSS Android device performance") in any comment or commit message, not by naming the device used for calibration. Any future contributor (human or AI) proposing a code/doc change that references a specific device/vendor name should be redirected to generic language before merge. This rule applies to third-party commercial hardware/device vendors only; references to the project owner's own other tools (e.g. Pembantu e-BKL) are not restricted by this ADR.
**Status:** Accepted. Backported 2026-07-29 from unmerged branch `sprint-gps-must-tier-import-20260723` (commit `362f545`, 2026-07-23) during a branch-triage pass; owner-confirmed at backport time.

### ADR-017
**Decision:** The Handheld GPS module (`FieldGpsLite.tsx`, `coordinate-parser.ts`, `CoordinateFinder.tsx`) will offer a **selectable coordinate system for display/output**, not just WGS84. Planned initial set, in priority order for the Sabah/Malaysia context:
1. **WGS84** (DD / DMS / DDM) — existing, default, capture format from `navigator.geolocation`
2. **BRSO Timbalai** (Borneo RSO, EPSG:29873 grid / EPSG:1236 datum shift) — Sabah/Sarawak cadastral standard
3. **GDM2000** (Geocentric Datum of Malaysia 2000, current national datum) — both Peninsular RSO and Borneo RSO grid variants
4. **UTM** (Zone 47N–50N as applicable) — general topographic/GIS interchange use
5. **Cassini-Soldner** — deferred/optional, only if a concrete cadastral-legacy use case arises; not part of initial scope

**Reason:** Malaysian land surveying practice routinely works across these systems depending on state (Sabah vs. Peninsular) and document vintage (older lots may still reference Cassini/Timbalai 1948). Restricting SabahLot to WGS84-only limits its usefulness as a field reference tool for licensed surveyors used to reading grid coordinates.
**Consequences:** `coordinate-parser.ts` currently exports `parseWgs84Coordinate()` only — no BRSO/GDM2000/UTM transform exists in this repo today. The Hotine Oblique Mercator (variant B) + datum-shift logic already verified to sub-1mm round-trip accuracy exists in the separate **Pembantu e-BKL** tool and should be **ported and adapted**, not rebuilt from scratch, to avoid re-deriving/re-verifying projection math. This is net-new scope beyond the accuracy-calibration work in ADR-016's context, and should be its own small sprint so the two changes can be tested and reviewed independently.
**Status:** Accepted (priority order and porting-from-Pembantu-e-BKL approach confirmed by owner 2026-07-29). **Not yet scheduled** — no sprint has been opened for this work; implementation must not begin without a separate, explicitly-scoped sprint. Backported from unmerged branch `sprint-gps-must-tier-import-20260723` (commit `362f545`, 2026-07-23, originally recorded there as "Proposed").

### ADR-019
**Decision:** `src/lib/land-records/feature-gate.ts`'s `isCloudReadEnabled()` gains a second, independent branch for `sabahlot-production` (ref `mrkhhdfxoomkzirwgnwx`), alongside its existing `sabahlot-dev` branch. The production branch is gated by **two conditions that must both hold**: `process.env.NODE_ENV === "production"` (exact match, unlike dev's `!== "production"`) AND a new module-level constant, `PRODUCTION_READ_ENABLED_CONSTANT`, which **ships `false`** in this sprint. This constant is deliberately never exported and has no runtime override (no env var, no query param) — the only way to change it is to edit `feature-gate.ts` and ship a new, separately-reviewed commit. `isCloudWriteEnabled()` is untouched: `sabahlot-production` is not accepted there under any `NODE_ENV`, so Production stays write-disabled regardless of this ADR.
**Reason:** Sprint `production-read-gate-phase1`, scoped 2026-08-04 following the owner's phased, read-before-write, module-by-module approach to eventually activating `sabahlot-production` (see PROJECT_STATE.md "Current approved next sprint" item 5, and ADR-018 for the target project itself). A single boolean flip on `NEXT_PUBLIC_SUPABASE_URL`/`NODE_ENV` alone was judged too easy to trigger by accident (a misconfigured Vercel env var) for a Production activation decision — the second, code-level, hardcoded switch means activation requires a deliberate, reviewed git commit, not just infrastructure config, and is trivially reversible (flip back to `false`).
**Consequences:** Merging this sprint's code to `main` does **not** by itself activate anything for a real user — `PRODUCTION_READ_ENABLED_CONSTANT` stays `false`, and Vercel's Production `NEXT_PUBLIC_SUPABASE_URL` has not been pointed at `sabahlot-production` (that's an owner-only action, `.env`/Vercel config is FORBIDDEN for any agent to touch). Actually flipping the constant to `true` is explicitly **out of scope** for this sprint and requires its own separate owner approval. `feature-gate.qa.ts` extended with Tests 8-13 covering the new `isTargetingSabahlotProductionProject()` matcher (fail-closed on missing/empty/malformed URL, lookalike/substring hostname rejection, case-insensitivity, non-https rejection) and the gate's behavior across all dev/production/neither URL × dev/production `NODE_ENV` combinations; the constant's own "if it were true" branch is documented, not executed, since exercising it would require a test-only export undermining the point of a non-runtime-configurable switch (see the comment above Test 8 in that file). No UI wiring, no new caller of `isCloudReadEnabled()` — behavior for every existing caller against `sabahlot-dev` is unchanged and regression-tested.
**Status:** Accepted and implemented (sprint `production-read-gate-phase1`, 2026-08-04). `npx tsc --noEmit` clean, `npx eslint .` 0 errors (31 pre-existing warnings, unchanged), `npm run build` succeeds, all 17 pre-existing `.qa.ts`/`.qa.tsx` suites re-run fresh with zero regressions, `feature-gate.qa.ts` 15/15 assertions PASS (9 pre-existing + 6 new). Committed and pushed (`96748a7`) after owner approval; opened as **PR #39**.

### ADR-020
**Decision:** A Production **write** path is opened strictly **per module**, never as a single blanket switch. `isCloudWriteEnabled()` (`src/lib/land-records/feature-gate.ts`) is left **completely untouched** — it is consumed identically by all five write-coordinators (`land_records`, geometry, points, parties, documents), and `src/app/page.tsx`'s save flow already calls all five unconditionally in one sequence, so a single Production branch added to it would have opened all five at once the instant its constant flipped. Instead, `land_records` gets its own dedicated function, `isCloudWriteEnabledForParentInProduction()`, gated by its own constant `PRODUCTION_PARENT_WRITE_ENABLED_CONSTANT` (ships `false`, same non-exported/no-runtime-override contract as ADR-019) **and** `NODE_ENV === "production"` **and** `isTargetingSabahlotProductionProject()`. It is called, OR'd with the existing `isCloudWriteEnabled()`, at exactly two real gate call-sites: `parent-ui-sync.ts`'s `syncParentLandRecordToCloud` (the actual UI-facing check) and `write-coordinator.ts`'s `createCloudLandRecord`/`updateCloudLandRecord` (defense-in-depth). Geometry/points/parties/documents coordinators are **not modified at all** — they keep calling only `isCloudWriteEnabled()`, so they stay closed to Production regardless of this ADR, structurally, not by convention alone.
**Reason:** Sprint `production-write-gate-phase2a-land-records`, scoped 2026-08-04, continuing the owner's phased, module-by-module Production rollout (ADR-018/019, PROJECT_STATE.md "Current approved next sprint" item 5). Investigating the existing write gate before implementing found it structurally incapable of expressing "just one module" — this ADR's per-module-function design is the fix, and sets the pattern any future write phase (2b geometry, 2c points, 2d parties, 2e documents) follows: its own function, its own constant, touching only its own coordinator, never `isCloudWriteEnabled()` itself.
**Consequences:** Merging this sprint's code does not activate anything for a real user — `PRODUCTION_PARENT_WRITE_ENABLED_CONSTANT` stays `false`. `feature-gate.qa.ts` gained Tests 14-17, the last of which is load-bearing: a static read of `geometry-write-coordinator.ts`/`points-write-coordinator.ts`/`parties-write-coordinator.ts`/`documents-write-coordinator.ts`'s actual source, asserting none of them ever reference `isCloudWriteEnabledForParentInProduction` — the structural proof this design actually holds, not just an assumption. `parent-ui-sync.qa.ts` gained Test 7a2, exercising the real call site (not just the gate function in isolation) with a fake Supabase client, proving zero network calls while the constant is false. `land-records-write.qa.ts` was not given a duplicate production-specific test — its env is pinned to `sabahlot-dev` for its whole run, so it only re-proves the pre-existing dev branch is unchanged (regression); the new production branch is fully covered by the other two files instead (documented in that file's own header comment, not silently skipped). As with ADR-019, flipping the constant to `true` is out of scope here, and should not happen — as a process precondition, not a code-enforced one — before Phase 1 (read) is confirmed stable in real Production traffic.
**Status:** Accepted and implemented (sprint `production-write-gate-phase2a-land-records`, 2026-08-04). `npx tsc --noEmit` clean, `npx eslint .` 0 errors (31 pre-existing warnings, unchanged), `npm run build` succeeds, all 17 pre-existing `.qa.ts`/`.qa.tsx` suites re-run fresh with zero regressions. `feature-gate.qa.ts` 19/19, `parent-ui-sync.qa.ts` 16/16, `land-records-write.qa.ts` 16/16 — all PASS. Committed and pushed (`f234a2d`) after owner approval; folded into **PR #39**. Production write for `land_records` remains inert regardless of when this merges; activating it, and every subsequent module's own phase, are separate future decisions not authorized by this ADR.

### ADR-030
**Decision (backfilled, retroactive):** A cloud `land_record_geometries` row's `id` is always the client-generated id of the `drawing_objects` entry it came from — never the parent `land_record`'s own id, and never a freshly-generated id at sync time. `syncParentGeometryToCloud()` (`child-ui-sync.ts`) syncs exactly one authoritative polygon per parent: the `drawingObjects` entries are filtered to `geometryType === "polygon" && category === "parent_lot"`; zero matches leaves geometry local-only (`no_parent_geometry`), and more than one match is rejected outright (`invalid_input`, "More than one parent-lot polygon is active") rather than guessing which one is authoritative. The chosen candidate's own `id` is looked up against the parent's cached `geometries` array: a match means UPDATE (using the cached row's `updatedAt` as the optimistic-concurrency token); no match with a *different* cached geometry present means the sync is refused (`invalid_input`, "already has a different cloud geometry") rather than silently replacing it; no match with no other cached geometry means CREATE, with the drawing object's own `id` and the parent's `landRecordId` spread in explicitly.
**Reason:** This choice was made during PR #24 (`sprint-02c2/child-ui-sync`, geometry UI wiring) but never recorded as its own ADR at the time — flagged as a gap in a later documentation-reconciliation pass (`docs/ai/PROJECT_STATE.md`'s Housekeeping section) and backfilled here on explicit owner instruction, once the Listing Partner module's sprints freed up capacity for repo housekeeping. Two other, independently-developed branches attempted the same problem with the opposite id-mapping choice — reusing the *parent land record's own id* for the geometry row instead of a `drawing_objects` entry's id (`sprint-02d1b-points-cloud-write` and `codex/geometry-ui-wiring`, both confirmed via `git cherry` to have no commit missing from `main` — i.e. genuinely superseded, not silently dropped). PR #24's `drawing_objects`-id approach was preferred because it keeps a `land_record_geometries` row's identity tied to the specific drawn shape that produced it (matching how points/parties/documents already key off their own client-generated capture-time ids, ADR-001), rather than overloading the parent's id onto a conceptually distinct child row — and because `land_record_geometries` is designed to eventually hold more than one geometry per parent (proposed lots, etc.), which a parent-id-keyed row could never support even in principle.
**Consequences:** A `land_record`'s cloud geometry identity is permanent from the moment a `parent_lot` polygon first syncs — renaming or otherwise editing that same drawn shape later reuses its `id` (an UPDATE), while deleting it and drawing a brand-new `parent_lot` polygon produces a genuinely new geometry row (a different `id`, a CREATE) rather than overwriting the old one in place. The "exactly one `parent_lot` polygon, or stay local" rule means a user who ends up with two `parent_lot`-categorized polygons at once (e.g. via import) gets an explicit rejection message on save, never a silent pick of one over the other. This ADR does not change any code — it documents the design PR #24 already shipped and that remains live on `main` today, unmodified since.
**Status:** Accepted (retroactive documentation only, 2026-08-04, no sprint ID — owner-approved housekeeping pass). No migration, no code change; `child-ui-sync.ts`'s behavior verified against this description by direct code read before writing this entry, not from memory. `child-ui-sync.qa.ts` (8/8, covering exactly this logic — one/zero/multiple `parent_lot` candidates, cached-id match vs. mismatch, stale/duplicate conflict mapping) re-run fresh as part of this pass's verification, zero regressions.

### ADR-031
**Decision:** A new, independent, permissive SELECT policy, `profiles_select_admin`, is added to `profiles`: any row is readable by a caller whose own `profiles.role = 'admin'`. Same second-independent-permissive-policy shape as ADR-029's `listing_partners_select_admin` — grants read only, alongside (never replacing) the existing `profiles_select_own`; Postgres combines multiple permissive policies with `OR`, so this can only ever add visibility for an admin caller, never narrow what a non-admin user already sees of their own row. `profiles_insert_own`, `profiles_update_own`, and the `prevent_profile_role_escalation` trigger are all unchanged.
**Reason:** Building the first slice of the general Admin Dashboard module (`sprint-admin-dashboard`, member growth/region stats) surfaced the same class of gap ADR-029 closed for `listing_partners`: `profiles`' only SELECT policy is `profiles_select_own`, so there was no way for an admin to read member counts, signup dates, or regions beyond their own single row.
**Consequences:** `listProfilesForAdminStats` (`dashboard-stats-repository.ts`) — a plain, unfiltered `SELECT created_at, region FROM profiles` — will return every row for an admin caller and only the caller's own row for anyone else, entirely via RLS; the function itself never checks or accepts a role/permission argument (ADR-006). It deliberately selects only `created_at`/`region`, never `full_name`/`phone`, even though this policy's grant would permit reading those too (Security invariant, brief). `use-admin-guard.ts`'s role check is a UX convenience only, same posture as ADR-029 — a non-admin visiting `/admin` sees a clear message, never a silently-empty or broken dashboard, but the real restriction is this RLS policy.
